01Architecture Overview

The app uses a dual-API strategy. Every data request tries a primary API first (/api/v2/* served from the same origin). If it fails, it falls back to a proxy backend at rolexcoderz.in/PWx which forwards authenticated requests to the real PW servers. The batch catalog itself is served from a static GitHub Pages JSON file.

02Application Routes (React Router)

Six routes drive the entire SPA. Route params (:batchId, :subjectId, :topicId, :lectureId) map directly to API arguments.

/
Home — batch catalog. Loads batches.json and renders the grid of batch cards.
/batches/:batchId
Batch detail page. Tabs: Subjects & Live Classes. Calls batch-details API; subjects list rendered as cards.
/batches/:batchId/subject/:subjectId/topics
Subject topics list. Each topic shows video / notes / exercise counts.
/batches/:batchId/subject/:subjectId/topic/:topicId/content
Topic content. Sub-tabs: Videos, Notes, DPPs. Paginated content list.
/player/:batchId/:subjectId/:topicId/:lectureId
Video player. Loads content list + schedule details, builds a vidcloud player URL. :lectureId = schedule_id.
/verify
Access verification. Code generation + 24-hour token activation.

09Video Player Pipeline

The player route loads the content list + schedule, finds the matching lecture, then constructs a vidcloud.eu.org player URL. VPLink is used only to shorten verify-URLs for Telegram sharing.

GEThttps://vidcloud.eu.org/play.php?{URLSearchParams}Player

Query params built by the frontend

https://vidcloud.eu.org/play.php??
  batch_id   = {batchId}
  subject_id = {subjectId}
  topic_id   = ""                          // always empty
  video_id   = {lecture._id || schedule._id || url}
  video_url  = ""                          // always empty
  video_name = {lecture.topic || schedule.name}
  video_img  = {videoDetails.image || fallback}
  video_type = "new"
  play_type  = "Lecture"
GEThttps://vplink.in/api?api={key}&url={encoded}Shortener

fetch(`https://vplink.in/api?api=${_g}&url=${encodeURIComponent(url)}`)
  → { "status": "success", "shortenedUrl": "https://vplink.in/xxxxx" }
API key _g is hardcoded in the bundle — see Constants. Used only to shorten the verify redirect URL before sending users to Telegram.

10Access Control & Verify Flow

A lightweight 24-hour gate. Users generate a code, share it via Telegram, then activate. A token is stored in localStorage and checked on every protected route. The whole mechanism is client-side (XOR + base64) — not cryptographically secure.

STEP 1
Generate code — PEEDA-XXXXXX
6 random chars from ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789, prefixed with PEEDA-. Stored in localStorage as asm_pending_auth_code.
STEP 2
Build verify URL — /verify?code=PEEDA-XXXXXX&redirect=...
Shortened via VPLink, then user is sent to Telegram channel t.me/asmultiversein.
STEP 3
Enter code on /verify
Validated against (a) a hardcoded list Zg, or (b) the locally-generated asm_pending_auth_code.
STEP 4
Activate 24h token — Hg()
Token = btoa(XOR(Date.now(), "as-multiverse-24h-token-secret")) → base64url. Stored as asm_access_token; expiry asm_token_expiry = now + 86400000.
STEP 5
Gate check — vn() on protected routes
If no valid token, redirect to /verify?redirect={currentPath}. Player route guards this in useEffect.
Hardcoded valid codes
Zg = ["ADMIN2026", "VIPPASS", "LO-IS-KING", "GODMODE", "ASMFREE2026"]
Entering any of these codes (case-insensitive, uppercased) instantly grants 24h access — no Telegram needed.
